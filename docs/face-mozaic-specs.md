# 顔ぼかし自動化ローカルアプリ 仕様書

- **バージョン**: v0.3（Mac実装フェーズ・Git連携ワークフロー前提）
- **作成日**: 2026-09-13
- **想定作成物**: 街中散歩動画の顔に自動でモザイク/ぼかしをかけるローカルCLIツール

---

## 1. 背景・目的

現在、YouTube用の街中散歩動画の顔モザイク処理にAVCLabs Video Blur AIを使用している。性能には満足しているが、以下の課題がある。

- 動画本数が多くなると、同じ操作（顔ぼかし設定→処理実行）を手作業で繰り返す必要がある
- アプリ側にバッチ処理・自動化機能がなく、UI構成上Pythonなどからの外部操作（自動化）も困難

そこで、**顔ぼかし機能に特化し、フォルダ単位で複数動画を自動処理できるローカルAIアプリ**を独自に開発する。処理はすべてローカル完結（クラウド送信なし）とする。

---

## 2. 開発方針・フェーズ

| フェーズ | 内容 | 実行環境 |
|---|---|---|
| Phase 1（本仕様書の対象） | 単一〜複数動画に対する顔検出＋ぼかし処理の実装・動作検証 | MacBook Pro (M1 Max, RAM 64GB) |
| Phase 2（別途追記予定） | Windows (Copilot+ PC, Core Ultra 5 255H, RAM 32GB) 向けの追加実装。NPU（OpenVINO EP）活用による高速化を含む | Windows |

**Git/GitHubを介した引き渡しを前提とする**：Phase 1はMacBook Proでリポジトリを作成・実装し、GitHubにpushする。Phase 2はWindows機で同リポジトリをgit cloneし、そこから追加実装（NPU対応等）を行う。この前提に基づく実務上の注意点は2.1にまとめる。

Phase 2の内容（OpenVINO Execution Provider経由でのNPU実行、DirectML EPとの比較検証など）は、Phase 1完了後に本仕様書に追記する。

### 2.1 Git/GitHubを介した開発の注意点

- **リモートリポジトリ**：GitHub上にリポジトリを作成する（公開/非公開はユーザーの判断。顔ぼかし対象の実動画やテスト用サンプル動画は個人情報を含むため、**リポジトリには含めない**）
- **SCRFD等のONNXモデルファイル**：数十MB〜数百MBになる場合があり、通常のgitリポジトリにそのまま含めるのは非推奨。`models/`ディレクトリは`.gitignore`で除外し、代わりに**モデルのダウンロードURLとダウンロード手順（またはダウンロードスクリプト）をREADMEに明記**し、Windows側でも同じスクリプトで取得できるようにする
- **`.gitignore`の対象**：`models/`（学習済みモデル）、`venv/`等の仮想環境、`__pycache__/`、テスト用の動画ファイル、ローカルの設定ファイル（個人の入出力パス等を含む場合）
- **依存関係の再現性**：共通の依存関係は`requirements-common.txt`に、OS固有の依存関係（`onnxruntime`のビルド差等）は`requirements-mac.txt`／`requirements-windows.txt`に分けて管理する（5.2のディレクトリ構成参照）。Windows側では`pip install -r requirements-common.txt -r requirements-windows.txt`で環境を再現する
- **ブランチ運用**：`main`ブランチにMac実装を反映し、Windows側での追加実装は`windows-npu`等のフィーチャーブランチで進めてから統合する運用を想定（個人開発なので厳密なルールは不要だが、Mac版の動作を壊さないようにする観点で分けておくと安全）
- **README**：セットアップ手順をMac向け・Windows向けそれぞれ明記する（Phase 2着手時に追記）

### 2.2 リリース方法（GitHub Actions / CI-CD）

リリースはGitHub Actionsで自動化する。手動でのビルド・配布作業を減らし、Mac/Windows両方のビルドを一貫した手順で行うことが目的。

- **トリガー**：バージョンタグ（例：`v0.1.0`）のpushをトリガーとしてリリースワークフローを実行する
- **ワークフロー構成（案）**
  - `ci.yml`：`main`ブランチへのpush/PR時に実行。Lint・（あれば）テストの実行
  - `release.yml`：タグpush時に実行。`macos-latest`/`windows-latest`のmatrix戦略で、それぞれのOS上でPyInstallerによるビルドを行い、GitHub Releasesにアーティファクト（Mac用・Windows用の実行ファイル）を添付する
- **各OSランナーでの前提作業**：
  - ffmpeg導入（Mac: `brew install ffmpeg`、Windows: `choco install ffmpeg`等、ワークフロー内で実行）
  - SCRFD等のモデルファイルは`.gitignore`対象のため、ビルド前に`scripts/download_models.py`をCI上で実行して取得する
  - 依存関係は2.1で分けた`requirements-common.txt`＋OS別ファイルをそれぞれのジョブでインストールする
- **重要な制約（NPU関連）**：**GitHub-hosted Windowsランナーには実機のIntel Core Ultra NPUが搭載されていない**。そのため、CI上のWindowsビルドは「ビルドが正常に完成し、CPU実行で動作すること」の確認に留まる。OpenVINO EP／NPUでの実際の動作確認は、Phase 2で手元のWindows実機（Core Ultra 5 255H機）で別途行う必要がある
- **Mac版の未署名アプリについて**：Apple Developer署名・公証（notarization）は行わない前提とする（個人利用のため）。そのため初回起動時にGatekeeperの「開発元が未確認」という警告が出る点をREADMEに明記し、右クリックで開く等の回避方法を案内する
- **リリース物**：GitHub Releasesに、Mac用（.zip等）・Windows用（.zip等、`v0.1.0`以降windows対応が入ってから）のアーティファクトをそれぞれ添付する

## 3. 機能要件

### 3.1 入力

- 入力形式：**iPhone Pro最新モデルでの4K60fps以上撮影を主な想定とする**。標準的には`.mov`コンテナ・HEVC(H.265)・10bit・HDR（Dolby Vision、多くはProfile 8）で記録されることを前提とする
- フレームレートは、通常のカメラ撮影（スローモーションでない場合）は基本的にCFR（固定フレームレート）として扱う。ただし念のため、処理開始時に`ffprobe`等で平均フレームレートと実フレームレートの整合性を軽くチェックし、大きくズレる場合はログに警告を出す（VFR特有の複雑な補正処理はPhase 1では実装しない）
- 動画の回転メタデータ（縦持ち撮影時など）を正しく解釈し、顔検出・出力の両方で向きが崩れないようにする。フレーム読み込みはOpenCVの`VideoCapture`単体ではなくffmpeg経由（回転・色空間メタデータを認識できる）を基本方針とする
- 入力方法（**以下3パターンすべてをPhase 1の必須要件とする**）：
  - 単一ファイル指定
  - 複数ファイルを選択しての一括指定（ファイルパスを複数指定）
  - フォルダ指定（フォルダ内の動画ファイルすべてを一括処理対象とする。再帰的／直下のみの両対応）
- 音声トラックを保持する

### 3.2 顔検出・ぼかし処理

- 動画の各フレームに対して顔検出を行い、検出した領域にぼかし/モザイク処理を適用する
- 検出モデル：**SCRFD**（ONNX形式、Hugging Face配布モデルを使用）を第一候補とする
  - モデルサイズ（2.5G/10G/34G等）は精度と速度のトレードオフを検証の上、設定で切り替え可能にする
- フレーム間の検出結果を安定化させるため、簡易トラッキング（IoUベースの追跡、または直近Nフレームの検出結果補間）を実装し、ぼかし範囲のちらつき・検出漏れフレームでの「素通り」を抑制する
- ぼかし方式は以下を選択可能にする（AVCLabs側の設定と揃えられるよう選択式にする）
  - ガウスぼかし（強度パラメータ）
  - モザイク（ブロックサイズパラメータ）
- 検出範囲のマージン（顔バウンディングボックスに対する拡大率、縦横別）を設定可能にする
- **前後フレームへのぼかし延長（フレームパディング）**：自転車走行中の人物やランナーなど、動きの速い被写体では、モーションブラーや一瞬の顔の向き変化により顔検出が途切れるフレームが発生し得る。これに対応するため、顔が検出されたフレームの**前Nフレーム・後Mフレーム**にも同じ領域（直前/直後の検出位置、またはトラッキングによる推定位置）へぼかしを適用できるようにする
  - 前フレーム数（N）・後フレーム数（M）はそれぞれ独立に設定可能とする（AVCLabs Video Blur AIにおいても「前」「後」を個別に設定でき、デフォルト0のところを3に変更して使うことが多いとのことなので、本アプリでも初期値は前後とも3を仮のデフォルトとし、Mac実装時の検証で調整する）
  - 延長フレームでのぼかし位置は、前後の検出結果から補間する（例：直前検出位置をそのまま流用、または前後の検出位置を線形補間）ことで、被写体が動いていてもぼかし位置が大きくズレないようにする
  - このパディング処理は3.2冒頭で述べたトラッキング／平滑化処理と連携させ、二重実装にならないよう設計する（トラッキングで補完しきれない検出途切れ区間に対するフォールバックとして機能させる）
  - パディングはフレーム数ベースで指定する（3.1で述べた通り、通常のカメラ撮影はCFRを前提とするため、フレーム数ベースの指定で実用上問題ないと判断する）

### 3.3 誤検知対策（動物・彫像・広告内の人物等）

街中散歩動画では、動物の顔、彫像・銅像、看板や広告・デジタルサイネージに映る人物の顔などを誤って検出するリスクがある。完全な誤検知ゼロは現実的でないため、段階的に対策を実装する。全ての対策に共通する大原則として、**「本物の人の顔を誤って除外してしまう（＝ぼかし漏れ）」ことを最優先で避け、判定に迷う場合は除外せずぼかす方向（安全側）に倒す**（4章の精度方針と整合）。

**設計上の原則（判定単位）**：3.3の各判定（動物除外・肌色判定・写真/絵画除外）は、**フレーム単位ではなく、トラッキングによって同一人物/物体と紐づけられた「トラック」単位で1回判定し、その結果をトラック全体に適用する**。フレームごとに判定すると、同一の人物・彫像でも数フレームおきに判定が入れ替わり、ぼかしが不自然に点滅する可能性があるため。

**Phase 1で実装する基本対策（低コスト）**
- 検出信頼度スコアの閾値調整（彫像・動物はスコアが低く出る傾向を利用）
- 最小顔サイズ（ピクセル数）による下限フィルタ（設定可能パラメータとする）
- SCRFDが出力する5点ランドマークの信頼度・幾何学的整合性チェックによるフィルタ
- 3.2の前後パディング／トラッキングと連動した、単発の誤検出（数フレームのみ出現）の除去

**Phase 1で実装する追加対策（処理速度低下は許容）**

1. **動物の除外（人間 vs 非人間の二値分類）**
   - 犬・猫・馬など動物種を個別に判定する必要はなく、「人間の顔か、それ以外か」の二値分類器を検出候補ごとに追加適用する設計とする（種類を限定しないため、リストにない動物にも対応できる）
   - 処理速度の低下は許容する前提のため、検出された全候補に対して逐次この分類器を通す
   - 実装候補：軽量な画像分類モデル（Hugging Face上の汎用画像分類モデル、またはCLIPのゼロショット分類等）をPhase 1実装時に選定する

2. **彫像・銅像の除外（肌色判定）**
   - 検出領域の色を**YCbCr色空間のクロミナンス成分（明るさの影響を受けにくい）**で判定し、人肌の色域から外れる場合は除外候補とする
   - 肌色域は東アジア系・白人・黒人・インド系など幅広い人種の肌色をカバーする広めのレンジで設定する（Mac実装時に実データで調整）
   - 大理石像など淡色の石像は肌色域と重なり除外できない場合があるが、その場合は「見逃し優先回避」の方針に従いぼかし対象のまま残す（＝彫像をぼかしてしまう誤りは許容し、本物の顔を除外してしまう誤りを避ける）
   - 4.1「色再現性」要件と密接に関連する（色空間の処理が不正確だと肌色判定の精度も低下するため、実装・テストを連動させる）

3. **写真・絵画中の人物の除外（オプション機能・デフォルトOFF）**
   - 単純に「連続フレームで表情・体勢の変化がない」ことだけを除外条件にはしない。実際に静止している本物の人物（信号待ち、休憩中、スマホ操作中など）も同様の見た目になり、見逃し（誤って除外）のリスクが高いため
   - 代わりに、以下を**すべて満たした場合のみ**除外候補とする複合条件とする
     - 顔の位置が、カメラの動き（パン・前進）に対して周辺背景と同じ動き方をしている（＝独立した動きがない）
     - かつ、顔内部の見た目（テクスチャ）がピクセルレベルで長時間ほぼ変化しない
     - かつ、判定に用いる継続時間（フレーム数）を長めに設定し、瞬間的な静止と区別する
   - それでも本物の静止人物を誤って除外するリスクを完全には排除できないため、**本機能はデフォルトOFFのオプションとして実装**し、Mac実装後の実動画での検証結果を見て、デフォルト有効化するか判断する

**Phase 1で仕組みだけ用意し、必要に応じて有効化する対策**
- **固定除外エリア（マスク）指定**：同じ散歩ルートで繰り返し映る彫像・看板などがある場合、動画内の特定領域を検出対象から除外できる設定を用意する（機械学習に頼らないシンプルな対策として優先度高）

**Phase 1では見送り、実運用で誤検知が問題になった場合に検討する発展的対策**
- 実際に発生した誤検知フレームを蓄積し、ハードネガティブとして検出モデルを追加学習する

Mac実装フェーズでの実測を踏まえ、各対策の閾値・要否を判断する。

> **要確認事項（ユーザー側で調査予定）**：AVCLabs Video Blur AIで現在使用しているぼかし方式（ガウス/モザイク）、強度・ブロックサイズの設定値、検出感度設定があれば、それに近づける形でデフォルト値を決定する。

### 3.4 出力

- 出力形式：入力と同じコンテナ/コーデック系統を基本としつつ、H.264/H.265を選択可能にする
- **画質設定（確定・推奨デフォルト）**：4K60fps以上のiPhone撮影を前提とし、固定ビットレート指定ではなく**CRF（Constant Rate Factor）ベースの品質指定**を既定とする（HEVC/libx265でCRF 18〜20程度を初期値の目安とし、Mac実装時の実測で調整する）。YouTube側で再エンコードされるため、配信用の最終圧縮を意識しすぎず、視覚的な劣化が分かりにくい品質を優先する
- 出力先：入力と別フォルダを指定可能（上書き事故防止のため、デフォルトでは入力を上書きしない）
- ファイル命名規則：`{元ファイル名}_blurred.mp4` を既定とし、変更可能にする
- 元動画の解像度・フレームレートを維持する

### 3.5 バッチ処理・自動化

- フォルダ内の複数動画を一括処理できること（本仕様の主目的）。3.1の3パターン（単一ファイル／複数ファイル選択／フォルダ全体）いずれの指定方法でも、対象となった動画すべてに対して同一パラメータで一括処理を行う
- 処理進捗（動画単位／全体）をコンソールに表示する
- 処理中断時に再開可能、または少なくとも「どこまで終わったか」がログで分かること
- 将来的にフォルダ監視（新規動画を自動検知して処理）まで拡張できる設計にしておく（Phase 1ではオプション、必須ではない）

### 3.6 パラメータ設定

- 上記の各パラメータ（モデルサイズ、ぼかし方式、強度、マージン、前後パディングフレーム数、検出閾値、出力コーデック等）は、コマンドライン引数または設定ファイル（YAML/JSON）で指定可能にする
- 動画ごとに個別パラメータを変えたいケースは現時点では想定しない（全動画共通設定でOK）

### 3.7 エラーハンドリング（確定方針・詳細はPhase 1実装時に調整）

- 破損した動画ファイル、非対応コーデック、ffmpeg未インストール、モデル読み込み失敗などが発生した場合、可能な限り具体的なエラー内容をログに出す
- **バッチ処理中に1本の動画でエラーが発生した場合は、そのファイルをスキップして残りの処理を続行する**（1本の失敗で全体が止まる方が不便なため、スキップ＆継続を既定動作とする）。処理後に「成功/失敗一覧」をログ・サマリーとして出力する
- ディスク空き容量については、Phase 1では厳密な事前チェックは行わず、書き込み失敗時に分かりやすいエラーメッセージを出すレベルに留める（4K60fps動画の一括処理で容量不足が実際に問題になった場合、Phase 2以降で事前チェック機能を追加検討する）

## 4. 非機能要件

- **処理方式**：完全ローカル処理、外部通信なし（プライバシー・著作権配慮の動画のため）
- **対応OS**：Phase 1はmacOS（Apple Silicon）、Phase 2でWindows対応を追記
- **パフォーマンス**：具体的な目標fpsは未設定。Phase 1でSCRFDの各モデルサイズでの実測値を取得し、実用速度（例：等倍速以上でのバッチ処理）を判断する
- **精度**：顔の見逃し（ぼかし漏れ）を最優先で避ける方針とする。誤検出（顔でない部分へのぼかし）は許容度が高い方向でパラメータ初期値を決める
- **拡張性**：モデル差し替え（SCRFD→YOLOv8Face等）が容易な構成にする（検出処理をインターフェース化）

### 4.1 色再現性（カラーマネジメント）要件

AVCLabs Video Blur AIをRyzen環境で実行した際、モザイク処理自体の品質はIntel CPU実行時と同等だったが、出力動画の色味が入力（iPhone撮影動画）に対して暗くなる現象が確認されている。これは、動画のデコード／エンコード処理系（CPU/GPUの実装差）において、色空間変換まわり（例：BT.601とBT.709の取り違え、フルレンジ／リミテッドレンジの取り違え、ガンマ処理の違いなど）に起因する可能性が高いと考えられる。本アプリでは同様の色ズレを起こさないことを明確な要件とする。

- **要件**：出力動画において、ぼかし処理の対象外領域（顔以外の部分）の色は、入力動画と実質的に同一（人が見て差が分からないレベル）であること
- **定量的な合否基準**：入力・出力動画から同一タイムスタンプのフレームを抽出し、ぼかし領域を除いた画素について、入力に対する平均絶対誤差（またはΔE2000などの知覚色差指標）が一定の閾値以下であることを自動テストで確認できるようにする（閾値は実装時にプロトタイプでの実測を基に決定する）
- **実装上の方針**：
  - フレームの読み込み・書き出しはOpenCVの`VideoCapture`/`VideoWriter`に任せきりにせず、色空間メタデータ（`color_space`, `color_range`, `color_primaries`, `color_transfer`）を入力動画から取得し、出力エンコード時（ffmpeg呼び出し部分）に明示的に指定・継承する
  - BGR/RGBの相互変換（OpenCVはBGR、多くのモデル・ライブラリはRGB前提）の際に、値のスケールやチャンネル順の取り違えが起きていないかをコードレビュー・テストで確認する
  - ハードウェアデコード／エンコード（Macであれば VideoToolbox等、Windowsであれば Intel Quick Sync等）を使用する場合、色空間情報が正しく維持されるかを個別に検証する。ソフトウェアデコードとの比較で色差が出る場合は、要件を満たす方（基本的にはソフトウェアデコード、または色空間指定を明示したハードウェアパス）を採用する
  - Phase 2（Windows移植）においても同様の検証を行い、AVCLabsで発生していたような色ズレがNPU/GPU実行パスで再発しないことを確認する

**HDR（Dolby Vision）への対応方針（確定）**：iPhoneでのHDR動画記録（Dolby Vision）を前提とするが、ダイナミックメタデータ（RPU）の完全な処理・再現はPhase 1では実装しない。代わりに、静的な色空間タグ（色域：BT.2020、伝達特性：PQ(smpte2084)またはHLG(arib-std-b67)、カラーレンジ等）を入力から取得し、出力にも同じタグを明示的に指定して書き込む方針とする。これは、以前確認された「色空間タグの取り違えによる色の暗転」という実際の問題に対して直接的に効く対策であり、Dolby Visionの完全なダイナミックトーンマッピング再現という難易度の高い実装を避けつつ、目的（色の見た目を変えない）を達成できると判断する。

強い希望がない項目について、以下をおすすめの仕様として確定した。

### 7.1 確定した推奨仕様（今回決定）

- **入力動画の前提**：iPhone Pro最新モデルでの4K60fps以上撮影（HEVC/.mov、10bit、HDR/Dolby Vision想定）を前提とする（3.1参照）

1. AVCLabs Video Blur AIの現行設定（ぼかし方式・強度・検出感度・前後パディング値）：分かればデフォルト値をより実態に近づけられるが、不明でもMac実装時の実測調整で対応可能なため、実装をブロックしない
2. 顔以外（例：ナンバープレート、看板の個人名等）へのぼかし要否：現時点ではPhase 1のスコープ外・将来のバックログ扱いとする
3. バッチ処理対象フォルダの典型的な動画本数・1本あたりの長さ：特定の制約は設けず、任意の本数・長さに対応できる設計（逐次処理＋ログ）とする

### 8.4 GUI実装方式の選定

UI実装方式として以下2案を比較検討した。

1. 内部処理・GUIともにすべてPythonで実装し、PyInstaller等でデスクトップアプリ化
2. 内部処理（モザイク処理）はPython、GUIはRust等で実装（プロセス分離）

**採用方針：案1（Python一本化）**

理由：
- 本アプリの処理時間のボトルネックは顔検出・動画エンコード等の重い処理であり、GUI描画性能ではないため、案2で得られる「GUIの速さ」のメリットが薄い
- 案2はPython⇔Rust間のプロセス間通信の設計や、Rust側へのPythonランタイム同梱など、GUI表示速度とは別の実装複雑さが増える割に、個人利用ツールとしてはリターンに見合わない
- 単一言語にすることで、Phase 1（CLI）のロジックをPhase 3（GUI）でそのまま再利用でき、開発・保守がシンプルになる

案1採用にあたっての実装上の留意点：
- GUIフレームワークは**PySide6（Qt for Python）**を候補とする（動画プレビューキャンバス・矩形描画・スライダー等が揃っており、Mac/Windows両対応、LGPLライセンス）
- 顔検出・動画処理などの重い処理は、GUIのメインスレッドとは別スレッド/プロセスで実行し、処理中にUIがフリーズしない設計にする
- PyInstallerでのパッケージング時、`onnxruntime`（特にOpenVINO EP/CoreML EP使用時）や`ffmpeg`バイナリの同梱でつまずきやすいため、Phase 1のCLI実装時から依存関係をできるだけシンプルに保ち、Phase 3でのパッケージングに備える
- PyInstallerはクロスコンパイル非対応のため、Mac版はMac上で、Windows版はWindows上でそれぞれビルドする必要がある

### 8.5 その他の検討事項

- プレビュー表示のための処理速度（全フレームの顔検出を事前に走らせる必要があるため、動画が長い場合の待ち時間をどう扱うか）

2. **キュー管理・処理順序変更・選択変換と競合防止**:
   - **処理順序の変更 (Reordering)**:
     - **マウスドラッグ＆ドロップ**: キュー内の行を直接ドラッグして任意の位置へ直感的に並び替え可能。
     - **▲ Up / ▼ Down ボタン**: 選択行をボタン押下またはショートカットキー（`Alt+Up` / `Alt+Down`）で1行ずつ移動。
     - **コンテキストメニュー**: 「▲ Move Up」「▼ Move Down」「⤒ Move to Top」「⤓ Move to Bottom」から素早く先頭・末尾へ移動可能。
     - **実行中ワーカースレッドとの動的同期**: 動画処理中に待機動画の順番を入れ替えた場合も、ワーカー側の未処理キューへ即時反映され、変更後の順番通りに処理を続行。
   - キューアイテムごとに一意の `item_id` (UUID) を付与し、スレッド間通信は `item_id` で同期。
   - 処理中や停止後にキュー内のファイルを削除しても、ワーカー内部のインデックスが狂わず安全に動作。
   - キュー内で特定の行を選択している場合、`▶ Start Processing (N selected)` となり選択項目のみを即座に再実行可能。未選択時は未完了アイテムを一括処理。
   - 右クリックメニューから「この動画を実行」「選択した動画を実行」「この動画以降を実行」「処理順序の移動」「キューから削除」を選択可能。

3. **Start / Stop ステートマシン**:
   - **待機中**: `▶ Start Processing`（青色・有効）
   - **実行中**: `⏹ Stop Processing`（赤色・有効）
   - **停止処理中**: `⏳ Stopping...`（グレー・非活性無効化）
     - バックグラウンドの FFmpeg プロセスおよびワーカースレッドがクリーンに終了するまでボタンを無効化し、多重実行や競合を防止。
   - **完了/停止後**: 自動的に待機状態へ復帰。

4. **Windows 完全サイレント起動＆ウィンドウポップアップ抑制**:
   - リポジトリ直下の `run.bat` から `scripts/run_gui.vbs` を経由して完全非表示で起動。
   - 変換中の FFmpeg / FFprobe / QSV コーデック判定を含むすべての子プロセスに `CREATE_NO_WINDOW` および `SW_HIDE` を適用し、黒いコマンド画面のポップアップを完全排除。

5. **スペック自動診断＆モデル自動選択**:
   - 起動時に CPU・物理RAM（32GB等）・DirectML GPU を診断し、ハイスペック環境では最高精度の `scrfd_34g_gnkps.onnx` を自動選択。

6. **フォルダ記憶 (`QSettings`) ＆ ドラッグ＆ドロップ**:
   - ファイル追加（`+ Add File(s)...`）、フォルダ追加（`+ Add Folder...`）、ドラッグ＆ドロップで最後に開いたパスを `QSettings.sync` で確実に永続化。

   - テスト実行時はレジストリを汚染しないよう `pytest` 用の分離設定 (`isolate_qsettings`) を採用。
