# 顔ぼかし自動化ローカルアプリ 仕様書

- **バージョン**: v0.3（Mac実装フェーズ・Git連携ワークフロー前提）
- **作成日**: 2026-09-13
- **想定作成物**: 街中散歩動画の顔に自動でモザイク/ぼかしをかけるローカルCLIツール

---

## 1. 背景・目的

現在、YouTube用の街中散歩動画の顔モザイク処理にAVCLabs Video Blur AIを使用している。性能には満足しているが、以下の課題がある。

- 動画本数が多くなると、同じ操作（顔ぼかし設定→処理実行）を手作業で繰り返す必要がある
- アプリ側にバッチ処理・自動化機能がなく、UI構成上Pythonなどからの外部操作（自動化）も困難

そこで、**顔ぼかし機能に特化し、フォルダ単位で複数動画を自動処理できるローカルAIアプリ**を独自に開発する。処理はすべてローカル完結（クラウド送信なし）とする。

## 2. 開発方針・フェーズ

| フェーズ | 内容 | 実行環境 |
|---|---|---|
| Phase 1（本仕様書の対象） | 単一〜複数動画に対する顔検出＋ぼかし処理の実装・動作検証 | MacBook Pro (M1 Max, RAM 64GB) |
| Phase 2（別途追記予定） | Windows (Copilot+ PC, Core Ultra 5 255H, RAM 32GB) 向けの追加実装。NPU（OpenVINO EP）活用による高速化を含む | Windows |

**Git/GitHubを介した引き渡しを前提とする**：Phase 1はMacBook Proでリポジトリを作成・実装し、GitHubにpushする。Phase 2はWindows機で同リポジトリをgit cloneし、そこから追加実装（NPU対応等）を行う。この前提に基づく実務上の注意点は2.1にまとめる。

Phase 2の内容（OpenVINO Execution Provider経由でのNPU実行、DirectML EPとの比較検証など）は、Phase 1完了後に本仕様書に追記する。

### 2.1 Git/GitHubを介した開発の注意点

- **リモートリポジトリ**：GitHub上にリポジトリを作成する（公開/非公開はユーザーの判断。顔ぼかし対象の実動画やテスト用サンプル動画は個人情報を含むため、**リポジトリには含めない**）
- **SCRFD等のONNXモデルファイル**：数十MB〜数百MBになる場合があり、通常のgitリポジトリにそのまま含めるのは非推奨。`models/`ディレクトリは`.gitignore`で除外し、代わりに**モデルのダウンロードURLとダウンロード手順（またはダウンロードスクリプト）をREADMEに明記**し、Windows側でも同じスクリプトで取得できるようにする
- **`.gitignore`の対象**：`models/`（学習済みモデル）、`venv/`等の仮想環境、`__pycache__/`、テスト用の動画ファイル、ローカルの設定ファイル（個人の入出力パス等を含む場合）
- **依存関係の再現性**：共通の依存関係は`requirements-common.txt`に、OS固有の依存関係（`onnxruntime`のビルド差等）は`requirements-mac.txt`／`requirements-windows.txt`に分けて管理する（5.2のディレクトリ構成参照）。Windows側では`pip install -r requirements-common.txt -r requirements-windows.txt`で環境を再現する
- **ブランチ運用**：`main`ブランチにMac実装を反映し、Windows側での追加実装は`windows-npu`等のフィーチャーブランチで進めてから統合する運用を想定（個人開発なので厳密なルールは不要だが、Mac版の動作を壊さないようにする観点で分けておくと安全）
- **README**：セットアップ手順をMac向け・Windows向けそれぞれ明記する（Phase 2着手時に追記）

### 2.2 リリース方法（GitHub Actions / CI-CD）

リリースはGitHub Actionsで自動化する。手動でのビルド・配布作業を減らし、Mac/Windows両方の配布用ZIPパッケージを一貫した手順で生成する。PyInstaller等の自己完結バイナリ化は依存ライブラリ（OpenVINO、PySide6等）の肥大化や環境非互換リスクがあるため、**各OSに必要なファイルのみを厳選したクリーンなZIP配布パッケージ方式**を採用する。

- **トリガー**：バージョンタグ（例：`v0.1.0`）のpush、またはGitHub上の手動実行（`workflow_dispatch`）
- **ワークフロー構成**
  - `ci.yml`：`main`ブランチへのpush/PR時に実行。macOS上での依存解決・テスト（pytest 63件）実行
  - `release.yml`：タグpush時に実行。`windows-latest`および`macos-latest`でそれぞれOS固有のZIPパッケージを生成し、GitHub Releasesに添付
- **パッケージ内容の分離（不要ファイルの徹底排除）**：
  - **Windows版 (`face-mosaic-windows.zip`)**:
    - `start-app.bat`（ワンクリック起動・初回進捗表示 / 2回目以降サイレント起動）
    - `scripts/setup_and_run.ps1`, `scripts/run_gui.vbs`, `scripts/download_models.py`, `scripts/benchmark.py`
    - `requirements/requirements-windows.txt`, `requirements/requirements-common.txt`
    - `face_mosaic/`, `configs/`, `assets/`, `LICENSE`, `README.md`
    - *(Mac固有のシェルスクリプトやrequirementsは一切含まない)*
  - **macOS版 (`face-mosaic-macos.zip`)**:
    - `start-app.command`（ダブルクリック起動ランナー、実行権限 `+x` 付与）
    - `scripts/setup_and_run_mac.sh`, `scripts/download_models.py`, `scripts/benchmark.py`
    - `requirements/requirements-mac.txt`, `requirements/requirements-common.txt`
    - `face_mosaic/`, `configs/`, `assets/`, `LICENSE`, `README.md`
    - *(Windows固有の `.bat`, `.ps1`, `.vbs` やrequirementsは一切含まない)*
- **Mac版の実行権限とGatekeeper対策**：
  - GitHub ActionsのmacOSランナー上で `chmod +x start-app.command scripts/*.sh` を適用した上で `zip -r -y` するため、macOSの「アーカイブユーティリティ」で展開した際に実行権限がそのまま維持される。
  - 未署名ファイルのGatekeeper警告に対しては、Finderでの「右クリック（Control+クリック）→ 開く」や `xattr -d com.apple.quarantine start-app.command` の案内をREADMEに明記して利用者の負担を最小化する。

## 3. 機能要件

### 3.1 入力

- 入力形式：**iPhone Pro最新モデルでの4K60fps以上撮影を主な想定とする**。標準的には`.mov`コンテナ・HEVC(H.265)・10bit・HDR（Dolby Vision、多くはProfile 8）で記録されることを前提とする
- フレームレートは、通常のカメラ撮影（スローモーションでない場合）は基本的にCFR（固定フレームレート）として扱う。ただし念のため、処理開始時に`ffprobe`等で平均フレームレートと実フレームレートの整合性を軽くチェックし、大きくズレる場合はログに警告を出す（VFR特有の複雑な補正処理はPhase 1では実装しない）
- 動画の回転メタデータ（縦持ち撮影時など）を正しく解釈し、顔検出・出力の両方で向きが崩れないようにする。フレーム読み込みはOpenCVの`VideoCapture`単体ではなくffmpeg経由（回転・色空間メタデータを認識できる）を基本方針とする
- 入力方法（**以下3パターンすべてをPhase 1の必須要件とする**）：
  - 単一ファイル指定
  - 複数ファイルを選択しての一括指定（ファイルパスを複数指定）
  - フォルダ指定（フォルダ内の動画ファイルすべてを一括処理対象とする。再帰的／直下のみの両対応）
- 音声トラックを保持する

### 3.2 顔検出・ぼかし処理

- 動画の各フレームに対して顔検出を行い、検出した領域にぼかし/モザイク処理を適用する
- 検出モデル：**SCRFD**（ONNX形式、Hugging Face配布モデルを使用）を第一候補とする
  - モデルサイズ（2.5G/10G/34G等）は精度と速度のトレードオフを検証の上、設定で切り替え可能にする
- フレーム間の検出結果を安定化させるため、簡易トラッキング（IoUベースの追跡、または直近Nフレームの検出結果補間）を実装し、ぼかし範囲のちらつき・検出漏れフレームでの「素通り」を抑制する
- ぼかし方式は以下を選択可能にする（AVCLabs側の設定と揃えられるよう選択式にする）
  - ガウスぼかし（強度パラメータ）
  - モザイク（ブロックサイズパラメータ）
- **ぼかし・モザイクの形状（Shape）**：
  - **丸型（楕円・Round / Ellipse）★デフォルト**: 顔の輪郭にフィットした楕円マスクでモザイクを適用。四角い不自然な角をなくし、背景への不要なかぶりを防止（アンチエイリアス境界処理）。
  - **四角形（Rectangle / Square）**: 従来の矩形マスク。
- 検出範囲のマージン（顔バウンディングボックスに対する拡大率、縦横別）を設定可能にする（デフォルト 50%）
- **前後フレームへのぼかし延長（フレームパディング）**：自転車走行中の人物やランナーなど、動きの速い被写体では、モーションブラーや一瞬の顔の向き変化により顔検出が途切れるフレームが発生し得る。これに対応するため、顔が検出されたフレームの**前Nフレーム・後Mフレーム**にも同じ領域（直前/直後の検出位置、またはトラッキングによる推定位置）へぼかしを適用できるようにする
  - 前フレーム数（N）・後フレーム数（M）はそれぞれ独立に設定可能とする（AVCLabs Video Blur AIにおいても「前」「後」を個別に設定でき、デフォルト0のところを3に変更して使うことが多いとのことなので、本アプリでも初期値は前後とも3を仮のデフォルトとし、Mac実装時の検証で調整する）
  - 延長フレームでのぼかし位置は、前後の検出結果から補間する（例：直前検出位置をそのまま流用、または前後の検出位置を線形補間）ことで、被写体が動いていてもぼかし位置が大きくズレないようにする
  - このパディング処理は3.2冒頭で述べたトラッキング／平滑化処理と連携させ、二重実装にならないよう設計する（トラッキングで補完しきれない検出途切れ区間に対するフォールバックとして機能させる）
  - パディングはフレーム数ベースで指定する（3.1で述べた通り、通常のカメラ撮影はCFRを前提とするため、フレーム数ベースの指定で実用上問題ないと判断する）

### 3.3 誤検知対策（動物・彫像・広告内の人物等）

街中散歩動画では、動物の顔、彫像・銅像、看板や広告・デジタルサイネージに映る人物の顔などを誤って検出するリスクがある。完全な誤検知ゼロは現実的でないため、段階的に対策を実装する。全ての対策に共通する大原則として、**「本物の人の顔を誤って除外してしまう（＝ぼかし漏れ）」ことを最優先で避け、判定に迷う場合は除外せずぼかす方向（安全側）に倒す**（4章の精度方針と整合）。

**設計上の原則（判定単位）**：3.3の各判定（動物除外・肌色判定・写真/絵画除外）は、**フレーム単位ではなく、トラッキングによって同一人物/物体と紐づけられた「トラック」単位で1回判定し、その結果をトラック全体に適用する**。フレームごとに判定すると、同一の人物・彫像でも数フレームおきに判定が入れ替わり、ぼかしが不自然に点滅する可能性があるため。

**Phase 1で実装する基本対策（低コスト）**
- 検出信頼度スコアの閾値調整（彫像・動物はスコアが低く出る傾向を利用）
- 最小顔サイズ（ピクセル数）による下限フィルタ（設定可能パラメータとする）
- SCRFDが出力する5点ランドマークの信頼度・幾何学的整合性チェックによるフィルタ
- 3.2の前後パディング／トラッキングと連動した、単発の誤検出（数フレームのみ出現）の除去

**Phase 1で実装する追加対策（処理速度低下は許容）**

1. **動物の除外（人間 vs 非人間の二値分類）**
   - 犬・猫・馬など動物種を個別に判定する必要はなく、「人間の顔か、それ以外か」の二値分類器を検出候補ごとに追加適用する設計とする（種類を限定しないため、リストにない動物にも対応できる）
   - 処理速度の低下は許容する前提のため、検出された全候補に対して逐次この分類器を通す
   - 実装候補：軽量な画像分類モデル（Hugging Face上の汎用画像分類モデル、またはCLIPのゼロショット分類等）をPhase 1実装時に選定する

2. **彫像・銅像の除外（肌色判定）**
   - 検出領域の色を**YCbCr色空間のクロミナンス成分（明るさの影響を受けにくい）**で判定し、人肌の色域から外れる場合は除外候補とする
   - 肌色域は東アジア系・白人・黒人・インド系など幅広い人種の肌色をカバーする広めのレンジで設定する（Mac実装時に実データで調整）
   - 大理石像など淡色の石像は肌色域と重なり除外できない場合があるが、その場合は「見逃し優先回避」の方針に従いぼかし対象のまま残す（＝彫像をぼかしてしまう誤りは許容し、本物の顔を除外してしまう誤りを避ける）
   - 4.1「色再現性」要件と密接に関連する（色空間の処理が不正確だと肌色判定の精度も低下するため、実装・テストを連動させる）

3. **写真・絵画中の人物の除外（オプション機能・デフォルトOFF）**
   - 単純に「連続フレームで表情・体勢の変化がない」ことだけを除外条件にはしない。実際に静止している本物の人物（信号待ち、休憩中、スマホ操作中など）も同様の見た目になり、見逃し（誤って除外）のリスクが高いため
   - 代わりに、以下を**すべて満たした場合のみ**除外候補とする複合条件とする
     - 顔の位置が、カメラの動き（パン・前進）に対して周辺背景と同じ動き方をしている（＝独立した動きがない）
     - かつ、顔内部の見た目（テクスチャ）がピクセルレベルで長時間ほぼ変化しない
     - かつ、判定に用いる継続時間（フレーム数）を長めに設定し、瞬間的な静止と区別する
   - それでも本物の静止人物を誤って除外するリスクを完全には排除できないため、**本機能はデフォルトOFFのオプションとして実装**し、Mac実装後の実動画での検証結果を見て、デフォルト有効化するか判断する

4. **イラスト・アニメ顔の除外（肌の局所分散・平坦度判定、Phase 3.5実装）**
   - ポスター、看板、アニメキャラクター、イラスト絵本などの顔検出をモザイク対象から自動除外する
   - 実写の人間の皮膚（毛穴、微細な凹凸、自然光のグラデーション、カメラノイズ）と、イラストの皮膚（デジタルセル画調の単色・ベタ塗り、平坦な階調）のテクスチャ特性の違いを利用
   - YCbCr色空間での肌色候補領域に対し、5×5局所ウィンドウの標準偏差（局所分散）を計算。局所分散が一定閾値未満の「平坦ピクセル比率（Flatness Ratio）」が65%以上かつ全体標準偏差が低い場合にイラスト顔と判定する
   - 単発フレームのノイズによる除外誤りを防止するため、トラッキング（`FaceTracker`）と連携し、複数サンプルフレームで全会一致（unanimous）してイラストと判定された場合のみトラックを除外する安全設計とする

**Phase 1で仕組みだけ用意し、必要に応じて有効化する対策**
- **固定除外エリア（マスク）指定**：同じ散歩ルートで繰り返し映る彫像・看板などがある場合、動画内の特定領域を検出対象から除外できる設定を用意する（機械学習に頼らないシンプルな対策として優先度高）

**Phase 1では見送り、実運用で誤検知が問題になった場合に検討する発展的対策**
- 実際に発生した誤検知フレームを蓄積し、ハードネガティブとして検出モデルを追加学習する

Mac実装フェーズでの実測を踏まえ、各対策の閾値・要否を判断する。

> **要確認事項（ユーザー側で調査予定）**：AVCLabs Video Blur AIで現在使用しているぼかし方式（ガウス/モザイク）、強度・ブロックサイズの設定値、検出感度設定があれば、それに近づける形でデフォルト値を決定する。

### 3.4 出力

- 出力形式：入力と同じコンテナ/コーデック系統を基本としつつ、H.264/H.265を選択可能にする
- **画質設定（CRF品質制御）**：固定ビットレート指定ではなく**CRF（Constant Rate Factor）ベースの品質指定**を既定とする。
  - **標準プリセット（既定値: CRF 23）**：視覚的な劣化をほぼ感じさせずに、元動画のファイルサイズを約50〜60%削減（容量半分）できる最適なバランス設定。
  - **最高画質プリセット（CRF 18）**：マスター・アーカイブ保存向けの超高画質設定（大容量）。
  - **容量優先プリセット（CRF 26）**：さらなる軽量化を図る設定。
- **ビット深度制御（10-bit / 8-bit）**：
  - `auto`（既定）：元動画のビット深度に応じる（HEVC時は10-bit HDRを維持）。
  - `8bit`：iPhone 10-bit HDR動画であっても8-bit (`yuv420p` / `nv12`) に変換して出力。BT.2020 / HLG等のカラータグは維持したままファイルサイズを大幅に削減し、WebやSNS、一般的なプレイヤーでの再生互換性を最大化する。
  - `10bit`：10-bitエンコードを明示的に指定。
- **MP4高速再生最適化（FastStart）**：
  - MP4/MOV出力時に `-movflags +faststart` を適用。動画ヘッダー（moov atom）をファイル先頭に配置し、大容量4K動画でもプレイヤーでの即時再生・シークおよびWebストリーミングを快適化する。
- 出力先：入力と別フォルダを指定可能（上書き事故防止のため、デフォルトでは入力を上書きしない）
- ファイル命名規則：`{元ファイル名}_blurred.mp4` を既定とする。
  - **パラメータ付与オプション（`append_params_to_filename`）**：有効時、適用したぼかし強度・マージン・CRFなどをサフィックスに付加（例: `{元ファイル名}_blurred_(G51-M50-CRF23).mp4`）。複数設定での比較・検証を容易にする。
- 元動画の解像度・フレームレートを維持する

### 3.5 バッチ処理・自動化

- フォルダ内の複数動画を一括処理できること（本仕様の主目的）。3.1の3パターン（単一ファイル／複数ファイル選択／フォルダ全体）いずれの指定方法でも、対象となった動画すべてに対して同一パラメータで一括処理を行う
- 処理進捗（動画単位／全体）をコンソールに表示する
- 処理中断時に再開可能、または少なくとも「どこまで終わったか」がログで分かること
- 将来的にフォルダ監視（新規動画を自動検知して処理）まで拡張できる設計にしておく（Phase 1ではオプション、必須ではない）

### 3.6 パラメータ設定

- 上記の各パラメータ（モデルサイズ、ぼかし方式、強度、マージン、前後パディングフレーム数、検出閾値、出力コーデック等）は、コマンドライン引数または設定ファイル（YAML/JSON）で指定可能にする
- 動画ごとに個別パラメータを変えたいケースは現時点では想定しない（全動画共通設定でOK）

### 3.7 エラーハンドリング（確定方針・詳細はPhase 1実装時に調整）

- 破損した動画ファイル、非対応コーデック、ffmpeg未インストール、モデル読み込み失敗などが発生した場合、可能な限り具体的なエラー内容をログに出す
- **バッチ処理中に1本の動画でエラーが発生した場合は、そのファイルをスキップして残りの処理を続行する**（1本の失敗で全体が止まる方が不便なため、スキップ＆継続を既定動作とする）。処理後に「成功/失敗一覧」をログ・サマリーとして出力する
- ディスク空き容量については、Phase 1では厳密な事前チェックは行わず、書き込み失敗時に分かりやすいエラーメッセージを出すレベルに留める（4K60fps動画の一括処理で容量不足が実際に問題になった場合、Phase 2以降で事前チェック機能を追加検討する）

## 4. 非機能要件

- **処理方式**：完全ローカル処理、外部通信なし（プライバシー・著作権配慮の動画のため）
- **対応OS**：Phase 1はmacOS（Apple Silicon）、Phase 2でWindows対応を追記
- **パフォーマンス**：具体的な目標fpsは未設定。Phase 1でSCRFDの各モデルサイズでの実測値を取得し、実用速度（例：等倍速以上でのバッチ処理）を判断する
- **精度**：顔の見逃し（ぼかし漏れ）を最優先で避ける方針とする。誤検出（顔でない部分へのぼかし）は許容度が高い方向でパラメータ初期値を決める
- **拡張性**：モデル差し替え（SCRFD→YOLOv8Face等）が容易な構成にする（検出処理をインターフェース化）

### 4.1 色再現性（カラーマネジメント）要件

AVCLabs Video Blur AIをRyzen環境で実行した際、モザイク処理自体の品質はIntel CPU実行時と同等だったが、出力動画の色味が入力（iPhone撮影動画）に対して暗くなる現象が確認されている。これは、動画のデコード／エンコード処理系（CPU/GPUの実装差）において、色空間変換まわり（例：BT.601とBT.709の取り違え、フルレンジ／リミテッドレンジの取り違え、ガンマ処理の違いなど）に起因する可能性が高いと考えられる。本アプリでは同様の色ズレを起こさないことを明確な要件とする。

- **要件**：出力動画において、ぼかし処理の対象外領域（顔以外の部分）の色は、入力動画と実質的に同一（人が見て差が分からないレベル）であること
- **定量的な合否基準**：入力・出力動画から同一タイムスタンプのフレームを抽出し、ぼかし領域を除いた画素について、入力に対する平均絶対誤差（またはΔE2000などの知覚色差指標）が一定の閾値以下であることを自動テストで確認できるようにする（閾値は実装時にプロトタイプでの実測を基に決定する）
- **実装上の方針**：
  - フレームの読み込み・書き出しはOpenCVの`VideoCapture`/`VideoWriter`に任せきりにせず、色空間メタデータ（`color_space`, `color_range`, `color_primaries`, `color_transfer`）を入力動画から取得し、出力エンコード時（ffmpeg呼び出し部分）に明示的に指定・継承する
  - BGR/RGBの相互変換（OpenCVはBGR、多くのモデル・ライブラリはRGB前提）の際に、値のスケールやチャンネル順の取り違えが起きていないかをコードレビュー・テストで確認する
  - ハードウェアデコード／エンコード（Macであれば VideoToolbox等、Windowsであれば Intel Quick Sync等）を使用する場合、色空間情報が正しく維持されるかを個別に検証する。ソフトウェアデコードとの比較で色差が出る場合は、要件を満たす方（基本的にはソフトウェアデコード、または色空間指定を明示したハードウェアパス）を採用する
  - Phase 2（Windows移植）においても同様の検証を行い、AVCLabsで発生していたような色ズレがNPU/GPU実行パスで再発しないことを確認する

**HDR（Dolby Vision）への対応方針（確定）**：iPhoneでのHDR動画記録（Dolby Vision）を前提とするが、ダイナミックメタデータ（RPU）の完全な処理・再現はPhase 1では実装しない。代わりに、静的な色空間タグ（色域：BT.2020、伝達特性：PQ(smpte2084)またはHLG(arib-std-b67)、カラーレンジ等）を入力から取得し、出力にも同じタグを明示的に指定して書き込む方針とする。これは、以前確認された「色空間タグの取り違えによる色の暗転」という実際の問題に対して直接的に効く対策であり、Dolby Visionの完全なダイナミックトーンマッピング再現という難易度の高い実装を避けつつ、目的（色の見た目を変えない）を達成できると判断する。

### 8.4 GUI実装方式の選定

UI実装方式として以下2案を比較検討した。

1. 内部処理・GUIともにすべてPythonで実装し、PyInstaller等でデスクトップアプリ化
2. 内部処理（モザイク処理）はPython、GUIはRust等で実装（プロセス分離）

**採用方針：案1（Python一本化）**

理由：
- 本アプリの処理時間のボトルネックは顔検出・動画エンコード等の重い処理であり、GUI描画性能ではないため、案2で得られる「GUIの速さ」のメリットが薄い
- 案2はPython⇔Rust間のプロセス間通信の設計や、Rust側へのPythonランタイム同梱など、GUI表示速度とは別の実装複雑さが増える割に、個人利用ツールとしてはリターンに見合わない
- 単一言語にすることで、Phase 1（CLI）のロジックをPhase 3（GUI）でそのまま再利用でき、開発・保守がシンプルになる

案1採用にあたっての実装上の留意点：
- GUIフレームワークは**PySide6（Qt for Python）**を候補とする（動画プレビューキャンバス・矩形描画・スライダー等が揃っており、Mac/Windows両対応、LGPLライセンス）
- 顔検出・動画処理などの重い処理は、GUIのメインスレッドとは別スレッド/プロセスで実行し、処理中にUIがフリーズしない設計にする
- PyInstallerでのパッケージング時、`onnxruntime`（特にOpenVINO EP/CoreML EP使用時）や`ffmpeg`バイナリの同梱でつまずきやすいため、Phase 1のCLI実装時から依存関係をできるだけシンプルに保ち、Phase 3でのパッケージングに備える
- PyInstallerはクロスコンパイル非対応のため、Mac版はMac上で、Windows版はWindows上でそれぞれビルドする必要がある

## 10. Phase 3.2 詳細仕様：長尺4K60fps対応・中断レジューム・NPU/GPU最適化

### 10.1 メモリ不足 (OOM) 防止アーキテクチャ
4K 60fps MOV 等の超高解像度・長尺動画（数万〜数十万フレーム）処理において、メモリ使用量が時間経過とともに増大してクラッシュする問題を根本解決：
1. **NumPy スライスによる 4K 生バッファ参照リークの遮断**:
   - `tracker.py` 内で検出顔を切り出す際、従来の `frame[y1:y2, x1:x2]` スライスは Python/NumPy の内部ポインタにより約 25MB の非圧縮 4K フレーム全体を保持し続けていた。
   - クロップ画像を長辺最大 128px にリサイズした上で、明示的に `.copy()` を呼び出して親フレームの生メモリ参照を即座に破棄。
   - トラックレットごとのクロップ保持上限を 35 枚に制限し、肌色・動物判定などのトラック評価完了後に蓄積バッファを自動解放。
2. **OpenCV C++ アロケータ制限の回避**:
   - `cv2.dnn.blobFromImage` によるメモリ割り当てエラーを防止するため、顔検出前処理を純粋な NumPy 演算（正規化・BGR→RGB反転・NCHW次元置換）に移行。
3. **プレビュー画像生成の軽量化**:
   - パイプライン内の GUI プレビュー画像転送時に、最大 640px 幅へ縮小してからコピーし、GUI 側での生フレーム蓄積を防止。

### 10.2 チェックポイント＆レジューム機構（中間状態保存と安全設計）
処理のクラッシュや予期せぬ中断時にも最初からやり直す必要をなくし、かつディスク容量を圧迫しない仕組みを確立：
1. **保存場所と階層構造**:
   - 出力先ディレクトリに `.{出力動画名}.checkpoint/`（隠しフォルダ）を作成。
   - 進行中の動画ファイルは `{出力動画名}.part.mp4` に書き出し、100% 完了時にアトミックに `.mp4` にリネーム。
2. **超軽量 JSONL 方式による不要キャッシュ防止**:
   - 非圧縮画像や動画キャッシュはディスクに一切保存しない。
   - 保存するのはメタデータ（`state.json`）と、各フレームの顔バウンディングボックス座標（`pass1_detections.jsonl`）。
   - 1,000 フレームあたり約 20KB、4K 60fps の 1 時間動画（約 21 万フレーム）でも数 MB 程度。
3. **自動クリーンアップ**:
   - パイプライン正常終了時に `.{出力動画名}.checkpoint/` は自動削除される。
4. **レジューム処理**:
   - Pass 1 途中で中断：記録された最終フレームからスキャンを再開。
   - Pass 2 途中で中断：Pass 1（AI推論）を全スキップし、Pass 2 から再開。

### 10.3 ハードウェア最適化 (CPU / Arc GPU / AI Boost NPU)
1. **OpenVINO による GPU + NPU ハイブリッド推論**:
   - Intel Core Ultra 環境で `openvino` を自動優先採用。
   - SCRFD モデルの動的入力を静的形状（`[1, 3, 640, 640]`）へ固定コンパイルすることで、NPU（Intel AI Boost）の制約をクリア。
   - `MULTI:GPU,NPU` または `GPU`（Intel Arc 130T）により **135〜155+ FPS** の超高速推論を実現。
2. **Pass 1 スケールダウン・ストリーミングデコード**:
   - 4K 解像度（3840×2160）をそのまま読み込むと、プロセス間パイプ転送が毎秒約 1.5GB に達し、デコード速度が約 2.4 FPS に制限されていた。
   - Pass 1 読み込み時に FFmpeg 内部で 640×360 にリサイズ（`-vf scale=640:360`）し、マルチスレッド（`-threads 0`）でストリーミング。
   - パイプ転送量を 1/36 に削減し、デコード速度を **約 2.4 FPS → 約 60 FPS（約25倍）** に高速化。

### 10.4 Pass 2 レンダリング高速化＆完全な色再現性保証
1. **Pass 2 の 3ステージ非同期並行パイプライン化**:
   - Windows 匿名パイプ経由での 4K 生フレーム転送ボトルネック（CPU 使用率 15% で停滞し 2.4 FPS に制限されていた要因）を解消。
   - ステージ 1（デコード）: `cv2.VideoCapture` を用いて Direct3D 11 / Media Foundation によるプロセス内ハードウェア高速デコードを行い、プリフェッチキュー（サイズ16）へ先読み。
   - ステージ 2（モザイク処理）: メインスレッドでメモリ上ゼロコピー演算（80+ FPS）。
   - ステージ 3（エンコード）: `VideoWriter` 内部に非同期ワーカースレッドを設け、Intel QSV（`hevc_qsv`）へバックグラウンドで連続ストリーミング。
   - Pass 2 の処理速度が **約 2.5 FPS → 約 20〜30+ FPS（最大10倍以上）** に高速化。
2. **色再現性・画質劣化の完全防止**:
   - 10-bit 階調の完全維持: 入力動画が 10-bit（`yuv420p10le`）の場合、エンコーダーでも自動的に 10-bit ピクセルフォーマット（`p010le`）を指定し、バンディングや色つぶれを防止。
   - HEVC VUI メタデータ注入: `-bsf:v hevc_metadata` により、BT.2020 広色域（`colour_primaries=9`）、HLG 伝達特性（`transfer_characteristics=18`）、マトリックス係数（`matrix_coefficients=9`）、レンジ（`color_range=tv`）をビットストリームの NAL ユニット内部に直接埋め込み。
   - YouTube や QuickTime、各種プレイヤーでの再生時に元映像と 100% 同一の色味・トーン・コントラストを保証。

## 11. Phase 3.4 詳細仕様：ハードウェア自動検知とマルチベンダー最適化

CPU、GPU、NPU アーキテクチャおよび RAM 容量を起動時に自動検知し、ハードウェア環境ごとに最適化された処理パイプラインへ自動分岐する。

### 11.1 ハードウェア検知アーキテクチャ (`hardware.py`)
- `get_hardware_vendor()`:
  - `apple_silicon`: macOS かつ arm64 アーキテクチャ / Apple Mシリーズプロセッサ
  - `amd_ryzen`: AMD Ryzen プロセッサ
  - `intel`: Intel Core / Intel Core Ultra プロセッサ
  - `generic`: その他一般的な x86_64 / ARM 環境

### 11.2 Apple Silicon (M1/M2/M3/M4) 向け最適化
1. **Pass 1 推論**:
   - ONNX Runtime において `CoreMLExecutionProvider` を最優先ロード。
   - Apple Neural Engine (ANE) および Metal GPU を利用して、低消費電力かつリアルタイム以上の高速推論を実行。
2. **Pass 2 レンダリング（動画エンコード）**:
   - macOS 専用ハードウェアエンコーダー **Apple VideoToolbox (`hevc_videotoolbox` / `h264_videotoolbox`)** を自動使用。
   - 10-bit HDR / BT.2020 維持: `-profile:v main10 -pix_fmt p010le` または `yuv420p10le` を自動指定し、QuickTime Player での完全な色再現性を保証。
   - 高効率・低発熱でバッテリー消費と CPU 負荷を最小化。

### 11.3 AMD Ryzen / Radeon 向け最適化
1. **Pass 1 推論**:
   - AMD Radeon GPU（内蔵または外付け）環境では `DmlExecutionProvider` (DirectML) により GPU 推論を活用。
   - CPU 実行時は、Zen アーキテクチャの強力な AVX2 / AVX-512 スループットを活かすため、`intra_op_num_threads` をマルチコア数に合わせて最適化。
2. **Pass 2 レンダリング（動画エンコード）**:
   - Radeon GPU 搭載時は **AMD AMF (`hevc_amf` / `h264_amf`)** を自動活用。
   - CPU ソフトウェアエンコード時（`libx265`）は `-threads 0` を明示指定し、Ryzen のマルチコア・マルチスレッド（16〜32スレッド）をフル稼働。

### 11.4 Intel Arc / Core Ultra 向け最適化（既存仕様完全維持）
- Intel Core Ultra / Arc GPU 環境では、これまでの実装通り **OpenVINO (`MULTI:GPU,NPU`)** による 135〜155 FPS の超高速推論と **Intel QSV (`hevc_qsv`)** によるハードウェアエンコードを最優先で維持。

### 11.5 安全なフォールバック機構
- いずれのハードウェア環境においても、ハードウェアエンコーダーの初期化に失敗した場合は即座にマルチスレッド `libx265`（CPU）へ安全に自動フォールバックし、動画処理の中断を防ぐ。

## 12. Phase 3.5 詳細仕様：丸型モザイクおよびイラスト顔除外フィルター

### 12.1 丸型（楕円）モザイク／ぼかしレンダリング
1. **課題の解決**:
   - 従来の四角形（矩形）バウンディングボックスによるモザイク処理では、顔の四隅に存在する背景（通行人、風景、看板など）まで余分に巻き込んでモザイク化され、不自然な四角いブロック感が目立っていた。
2. **アンチエイリアス楕円マスクアルゴリズム (`FaceBlurrer`)**:
   - 顔検出バウンディングボックス $(x_1, y_1, x_2, y_2)$ に対し、中心 $(c_x, c_y) = ((x_1+x_2)/2, (y_1+y_2)/2)$、長軸・短軸半径 $((x_2-x_1)/2, (y_2-y_1)/2)$ の楕円を定義。
   - `cv2.ellipse(..., lineType=cv2.LINE_AA)` により高品質アンチエイリアスマスクを生成。
   - ピクセルモザイク（Pixelation）およびガウスぼかし（Gaussian）双方において、マスク値を浮動小数アルファ値 $\alpha \in [0.0, 1.0]$ に正規化し、元画像とモザイク画像をアルファブレンド合成。
   - これにより、ブロック境界の階段状ジャギーを完全に解消し、顔の自然な輪郭に沿った丸みのある美しいモザイクを実現。

### 12.2 イラスト・アニメ顔自動除外フィルター (`IllustrationFilter`)
1. **課題の解決**:
   - 動画内に映り込む看板、広告ポスター、漫画・アニメのイラスト、本の表紙などに描かれた人物の顔にモザイクがかかってしまう誤検知を解消する。
   - 彫像・銅像と同様にイラスト顔をモザイク除外対象としつつ、実写の人間の顔は絶対に見逃さない高い安全性を両立する。
2. **アルゴリズム設計**:
   - **肌色領域の特定**: YCbCr 色空間において $80 \le Cb \le 135$ かつ $133 \le Cr \le 180$ の肌色候補ピクセルを抽出。
   - **局所テクスチャ分散（Local Variance / Flatness Ratio）**:
     - 実写の人肌は毛穴、皮膚のキメ、自然光の陰影グラデーション、カメラのセンサーノイズが存在するため、局所領域内（$5 \times 5$ カーネル）で有意な輝度分散を持つ。
     - 一方、イラスト・アニメの皮膚はデジタル単色塗り（セル画調）またはフラットシェーディングであり、局所標準偏差が極めて小さい（$< 3.0$）ピクセルが肌全体の $70\% \sim 95\%$ を占める。
     - 平坦ピクセル比率（`flatness_ratio`）が閾値（既定: 0.65）以上かつ全体標準偏差が小さい場合にイラスト顔と判定。
   - **解像度セーフティ**:
     - 短辺 16px 未満の極小領域は低解像度による平坦化と誤認するリスクを防ぐため、安全側（実写人間扱い）として判定をスキップ。
3. **トラッカー統合と全会一致判定**:
   - 単一フレームでの瞬間的な白飛び等による誤判定を防ぐため、`FaceTracker.evaluate_track_validity()` で軌跡からサンプリングされた複数クロップすべてがイラストと判定された場合（全会一致）のみトラックを除外。実写人間に対するモザイク漏れを徹底的に防止する。

### 13.2 パラメータ設定グリッドの人間工学レイアウト
利用者の思考順序および動画変換パイプラインの流れ（AI顔検出 → モザイク適用 → モザイク形状 → トラッキング → ファイル出力）に沿って、全5行のパラメータを論理的にペアリングして再配置：

| 行 | 左列パラメータ | 右列パラメータ | グルーピングの目的 |
|---|---|---|---|
| **Row 0** | **Model** (AIモデル) | **Detection Confidence** (検出閾値) | 顔検出エンジンの基礎スペックと感度設定 |
| **Row 1** | **Face Margin (%)** (顔拡大率) | **Blur Strength** (ぼかし強度/ブロック幅) | 顔のカバー範囲と秘匿強度の設定 |
| **Row 2** | **Blur Type** (Gaussian / Mosaic) | **Blur Shape** (Round / Rect) | ぼかしの描画方式および輪郭形状の指定 |

| **Row 4** | **Output Codec** (HEVC / H.264) | **CRF Quality** (動画画質) | 出力ファイルの圧縮形式およびエンコード品質 |
